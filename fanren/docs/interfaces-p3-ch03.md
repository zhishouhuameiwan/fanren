## 0. 为什么需要这一批

第 3 章要开三样新东西，现状都不具备：

1. **曲魂入队**——`GameState` 里根本没有队伍，只有背包、灵田、瓶子。
2. **用毒**——不存在。
3. **识海之战**——`BattlePhase` 只有 `Ongoing / Won / Lost / Escaped`，
   其中 `Escaped` 是**玩家**逃跑。**敌人逃走没有落点**（技术债 G-2 记着这一条）。
   而原著 ch56 那第二场，敌人是**必然逃走**的，战果按咬下多少计。

三样都不做，第 3 章只能退化成一串对话加两场普通战斗，本章的高潮就没了。

**这三样都要改 `src/core/model/Types.h`，所以由同一个人做，不要拆开并行。**

## 1. 队伍（`GameState`）

### 1.1 状态

`GameState` 末尾追加（**追加在末尾**，不得插在中间——会破坏按字段顺序写的聚合初始化）：

```cpp
struct PartyMember {
    std::string roleId;     // 对应 data/roles/
    int hp = -1;            // 当前气血；-1 表示「按角色模板满血」
    bool active = true;     // 是否参战。留着位置但不上场的同伴用得上
};

std::vector<PartyMember> party;   // 不含韩立本人；他是主角，不占队伍位
```

**韩立不进 `party`**：他的状态散在 `GameState` 的既有字段里（`hp` / `realm` / `cultivation` …），
硬塞进队伍会立刻出现「两处都记着他的血量」这种双重真源。

### 1.2 存档

- `kSaveVersion` 升到 **3**。
- 登记 **2→3** 的迁移。它是空操作（v2 本就没有 `party`），
  但**必须登记**：第 2 章已经证明「空操作」与「忘了登记」在行为上天差地别——
  后者直接把老玩家的存档判成不支持。
- 往返测试要覆盖：空队伍、一名同伴、`hp = -1` 与具体血量、`active` 两种取值。

### 1.3 脚本 API

```lua
party.add(role_id)        -- 入队。已在队里则什么都不做（幂等）
party.remove(role_id)     -- 离队
party.has(role_id)        -- 只读，返回 bool
party.size()              -- 只读，返回人数
```

写走命令队列，读走 `__host`，与既有分界一致。
命令 kind 追加在 `CommandKind` **末尾**：`PartyAdd` / `PartyRemove`。

`party.add` 传一个 `data/roles/` 里不存在的 id 时**回填 `ok = false`**，不要静默收下——
拼错的角色 id 会在战斗里变成一个没有属性的空单位，而那时已经很难追回是谁写错的。

### 1.4 战斗里怎么用

> **已被 docs/octopath-battle.md 取代**（八方旅人化改造，2026-09-25）：同伴上场、同一个角色不得出现两次的口径不变；站位随格子一起作废（新文档 6.1）。

`BattleScene` 组队时，除玩家外把 `party` 里 `active` 的成员按 `ally = true` 放上场。
`BattleSetup.units` 里已经写死的 ally 单位与 `party` 的关系由实现方定夺，
**但同一个角色不得同时出现两次**，要有测试。

## 2. 用毒

> **已被 docs/octopath-battle.md 取代**（八方旅人化改造，2026-09-25）：毒的结算原样沿用；新增「毒药撒出去算一击『毒』」「带毒的法术多一个『毒』类别」（新文档 2.2、2.7）。

### 2.1 范围（刻意做小）

**只做战斗内的状态，不做毒理系统。** 它服务于韩立备毒对付墨居仁这一段。

`Unit` 已有 `shield` / `stun` 两个状态字段，毒按**同样的方式**追加在末尾：

```cpp
int poison = 0;          // 剩余回合数
int poisonPower = 0;     // 每回合掉血
```

不新起结构、不做抗性、不做毒的种类。将来要扩再说。

### 2.2 结算

- 每回合固定时机扣血，扣多少与还剩几回合都要能在界面上看见。
- **中毒必须在界面上看得出来。** 玩家掉血却不知道为什么，一律会被当成 bug——
  这是本项目反复确认过的判据。
- 毒**不会**直接把单位打到 0 血以下致死还是会，由实现方定并在报告里说明理由；
  无论哪种，都要有测试钉住。

### 2.3 来源与解除

- 来源：物品（毒药）与法术各至少一条路径。
- 解除：物品（解毒药）。
- 两者都走既有的 `Item` / `Magic` 数据，不要在 game 层写死。

### 2.4 尸虫丸**不走这套**

尸虫丸是**剧情状态**：一个旗标加一个期限，不在战斗里结算。
把它做成战斗毒，玩家会以为吃颗解毒丹就能摆脱墨居仁的控制，那是另一回事。
这一条要写进代码注释，免得后人「顺手统一」。

## 3. 识海之战

> **已被 docs/octopath-battle.md 取代**（八方旅人化改造，2026-09-25）：吞噬规则原样沿用；两团改成两波（新文档第 8 节决策 9），格子与走位的说法作废。

### 3.1 原著的实际打法（`docs/ch03-design.md` 1.1 节，ch56 核对）

两场连着的，不是一场：

| 顺序 | 对手 | 体积 | 结果 |
| --- | --- | --- | --- |
| 一 | 黄光球 | 拇指大，**比韩立小好几倍** | 靠体积**轻易吞掉** |
| 二 | 绿光球 | **比韩立大一圈** 但虚弱，是个空架子 | 败而逃，**每被咬住就脱开那块继续跑**，最终逃脱，体积少三分之一 |

### 3.2 `BattlePhase` 增加敌方逃遁

```cpp
enum class BattlePhase { Ongoing, Won, Lost, Escaped, EnemyFled };
```

追加在**末尾**。`Escaped` 是玩家跑了，`EnemyFled` 是敌人跑了，两者的后续剧情完全不同，
合并成一个会让脚本无法分辨。

**所有 `switch (phase)` 都要补上新分支**，且**不要加 `default:`**——
加了就消掉「新增枚举项忘了处理」的编译期告警，而那正是这次要靠的东西。

### 3.3 吞噬：用现有数值表达，不要另造一套

**体积即实力**，直接映射到 `maxHp`：

- 造成伤害时，攻击方按伤害量**增加 `maxHp` 与 `hp`**（吞噬使你变大）。
- 受伤方 `maxHp` 同步下降（被咬掉的那块没了）。
- 倍率与上限由实现方定，写进注释说明为什么是这个数。

这样不需要新的战斗子系统，第一场「靠体积轻易吞掉」与第二场「咬下三分之一」
用同一套规则自然成立。

### 3.4 第二场是设计上打不死的

敌人体积降到某个阈值时**必然逃走**，战斗以 `EnemyFled` 结束。

- 阈值与「脱开那块继续跑」的表现由实现方定。
- **战果要能被脚本读到**：脚本需要知道咬下了多少（原著是三分之一），
  因为章末余子童的状态与台词要对得上。
  建议在 `CommandResult` 上回填一个百分比或绝对值，具体口径由实现方定并写进本文。
- **玩家不能靠打得久把它打死。** 要有测试证明：无论打多少回合，结局都是 `EnemyFled`。

### 3.5 这一场不用前两场的规则

识海里**没有法术、没有物品、没有地形、不能逃**。玩家刚学会的那套全不管用，
这种失重感正是这场戏要的。`BattleSetup` 已有 `can_escape`，
其余由战斗数据不登记法术与物品自然实现，不需要新开关。

> **2026-09-21 更正（引擎方）**：上面那句「自然实现」当时是真的，但真得没有道理——
> 那阵子 `BattleState::addMagic` / `addItem` 在**产品代码里一次都没被调用过**
> （只有单测在调），于是**每一场**战斗都不登记，识海只是碰巧和别人一样。
> 碰巧成立的东西会在别处一变就塌：别的战斗一旦开始登记，这一条就没了。
> 现在登记由 `BattleScene::buildFromSetup` 统一做，识海是一条**明写的例外**，
> 口径见 5.4，由 `tests/Ch03BattleKitTests.cpp` 的
> `TheMindBattleRegistersNothingAtAll` 与 `TheSoulCannotThrowAFireballInsideTheMind`
> 钉着。后者还配了「把例外去掉会怎样」的同局对照。

## 4. 测试要求

**每一条新行为都要有测试，且要有负向用例。** 最低要求：

1. `party.add` 幂等；传不存在的 role id **回填失败**（负向）。
2. 队伍存档往返：空、一人、`hp = -1`、具体血量、`active` 两种取值。
3. **2→3 迁移已登记**（负向对照：未登记的版本要在版本检查这一步就被挡下）。
4. 战斗组队：`party` 里 `active` 的成员上场；同一角色不得出现两次（负向）。
5. 中毒每回合掉血、回合数递减、可被解除；**界面上看得见**（断言那串字确实有内容，
   不要写成「找不到某个词就算过」——那种断言在字符串变空时照样通过）。
6. 识海第一场：体积小的敌人可被吞掉，吞完后玩家 `maxHp` 确实变大。
7. **识海第二场必然 `EnemyFled`**：打 200 回合也不会 `Won`（负向：把阈值改掉会让它转红）。
8. 咬下的战果可被脚本读到，且与实际伤害对得上。

**本项目最惨的一次事故是校验器的正则被吃掉转义、从此永远报通过而无人发现，
因为没人做过负向验证。只报告「测试通过」而没跑过负向用例的，视为没做完。**

已知的判据空转法见 `docs/README.md` 那张表（正则被吃、字符串变空、禁词表清空、
比值分母塌成 0、只钉一个点、陈旧二进制、读错日志），写断言前逐条对照。

## 5. 实现回执：契约留给实现方定的那些口径（2026-09-21 落地）

本节由引擎方在施工后补写，把上面几处「由实现方定并写进本文」的地方定稿。
**编剧与关卡照本节调用。** 其中 5.3 的第二条是对契约 3.3 的**一处收窄**，
理由写在那里，不是默默偏移。

### 5.1 队伍

| Lua | 返回 | 失败时的 `code` |
| --- | --- | --- |
| `party.add(role_id)` | `ok`（布尔） | `"no_role"`：`data/roles/` 里没有这个 id |
| `party.remove(role_id)` | `ok`（布尔） | `"not_in_party"`：他本来就不在队里 |
| `party.has(role_id)` | 布尔 | — |
| `party.size()` | 整数 | — |

- `party.add` **幂等**：已在队里时不改动任何字段（不会把带伤的同伴重置成满血），
  但仍回填 `ok = true` ——「让他入队」这件事的结果已经成立。
- `party.remove` 的 `ok` 是「是否真有人离队」，与 `take()` 同一个口径。
- 战斗编成（1.4 节）：`BattleSetup.units` 里已写死的 ally 单位**优先**，
  队伍成员与它们**按角色 id 去重**，撞上的那一位不上场；主角 `hanli` 同理，
  他是 0 号单位，队伍里就算混进一条 `hanli` 也不会在场上出现第二个。
  站位从主角出生点向外一圈圈找第一个空格，找不到就不上场（不叠格）。
- 打完一场普通战斗，同伴的气血写回 `PartyMember::hp`；识海那一场不写回（见 5.3）。

### 5.2 用毒

> **已被 docs/octopath-battle.md 取代**（八方旅人化改造，2026-09-25）：`useRange` / `castRange` 已删，其余字段照旧。

数据字段（`data/items/**` 与 `data/magics/**`，加载器已支持）：

| 字段 | 位置 | 含义 |
| --- | --- | --- |
| `poison` | Item / Magic | 中毒回合数 |
| `poisonPower` | Item / Magic | 每回合掉血 |
| `curesPoison` | Item | 解毒（布尔） |

- `poison` 与 `poisonPower` **必须同时给出**，只写一半在加载时报错；
  负数报错；一件东西既下毒又解毒报错。
- 毒药以敌方为目标，丹药与解毒药以己方为目标，**按数据分流**（`item.poison > 0`），
  引擎不认识任何具体物品 id。
- 结算在**回合开始**，先于眩晕；**不走护体罡气**（罡气挡的是外力）。
- **毒不致死，最低留 1 点气血。** 理由：本章的毒是韩立对付墨居仁的手段，
  而墨居仁必须死在识海反噬上（大纲硬约束第 6 条）；且回合开始时无人行动，
  此刻判死会让玩家看到「什么都没发生，然后我输了」。
- 续毒不叠加：回合数取长、强度取高。
- 界面：单位气血下面一行「中毒 N 回合（每回合 M 点）」，两个数都写出来。
- 引擎方为落 schema 与写测试加了两条真数据：`pill_shixin_san`（毒）、
  `pill_qingdu_san`（解毒），数值随手取，编剧可直接改或另起新条。
- **尸虫丸不走这套**（契约 2.5）。代码里三处注释钉着这一条：
  `core::Item`、`core::battle::Unit`、`data/items/pills/qingdu_san.json`。

### 5.3 识海之战

> **已被 docs/octopath-battle.md 取代**（八方旅人化改造，2026-09-25）：吞噬模式另把劲、架势、破绽、蓄势清零（新文档 2.9）。

- **开关挂在地形上**：`BattleSetup.terrain == "mind"` 即吞噬模式。
  不新增战斗 JSON 的字段（`io/BattleLoader.cpp` 不在本批的改动范围内，
  而为一个布尔值让每份战斗配置都多一个字段也不划算）。
- **一口咬多深**：`攻方当前 maxHp / 16`，至少 1。攻防、五行、境界压制
  在这一场一概不参与——识海里没有兵器也没有护甲，只有谁大。
  为什么是 16：韩立入梦体积 480 ÷ 16 = 30，正好是黄光球（`mo_juren_yuanshen`
  的 `maxHp = 120`）的四分之一，四口吞掉，对上原著「很快就结束了」；
  同时保证绿光球逃走前至少挨六口，每口都要玩家操作一次。
- **韩立在识海里的体积固定为 480**（`kDevourPlayerVolume`），不取存档里的 `maxHp`：
  识海比的是元神，用肉身气血当体积等于让「入梦前吃没吃丹药」决定梦里谁大谁小，
  而原著那三条体积关系是剧情硬约束。**这一场因此也不把气血写回存档。**
- **【对契约 3.3 的收窄】只有我方吃得下去。** 契约原文是「攻击方按伤害量增加
  maxHp」，实现改为：守方一律掉体积，**只有 ally 一侧的攻击者长体积**。
  双方都吞噬的话，大的那个滚雪球——第二场就成了绿光球反过来把韩立吃掉，
  与原著正相反。另两条理由：原著里贪吃的是韩立，入侵的两团是来夺舍的；
  这是韩立自己的识海，咬下来的能就地化为己有，入侵者咬下的那块只是被打散。
  收窄之后敌方体积**单调下降**，「必然逃走」成了结构性保证而非数值巧合。
- **谁逃得掉**：只有**开战体积大过韩立**的那一团才脱得开身。这一条是两场戏的
  分水岭：黄光球比韩立小好几倍，一口就是它的四分之一，第二口下去已经不成形，
  谈不上「把被咬住的那块脱开继续跑」，于是被整团吞掉；绿光球舍掉一块还剩得下
  自己。没有这一条，下面那个三分之一的阈值会把第一场那团也放跑。
- **逃遁阈值**：敌方体积掉到开战体积的三分之二以下（即被咬掉三分之一）即遁走，
  本场以 `EnemyFled` 结束。这个数不是平衡旋钮，它就是原著的战果。
  又因为吞噬模式下 `hp` 与 `maxHp` 同增同减，敌方 `hp` 恒等于 `maxHp`，
  于是**它必然在剩三分之二时逃走，绝不可能先被打到 0**——打不死是结构性的。
- **战果口径**：`CommandResult.value` = 逃走那一方**被咬掉的体积百分比（0-100，
  四舍五入）**，没人逃走时为 0；`CommandResult.code` 带回结局：
  `""` 赢 / `"lost"` / `"escaped"`（我方跑了）/ `"enemy_fled"`（敌人跑了）/
  `"unfinished"`（驱动方没打完，正常流程不会出现）。
- **脚本侧**：`battle(id)` 现在返回三个值 `won, how, spoils`。
  只看第一个的老脚本照旧能用；**识海第二场必须看第二个**——那一场
  `won` 永远是 `false`，只看 `won` 会把「敌人带着伤跑了」读成「韩立输了」。

```lua
local won, how, spoils = battle("b03_shihai_duoshe")
if how == "enemy_fled" then
    flag.set("ch03.shihai_yaoxia", spoils)   -- 原著是三分之一，实测 33-45
end
```

- `data/battles/b03_shihai_duoshe.json` 已按 1.1 节那张表重做成**两团**：
  `mo_juren_yuanshen`（`maxHp 120`，韩立体积的四分之一，被整团吞掉）与
  `yu_zitong`（`maxHp 660`，480 的 1.4 倍，咬掉三分之一后遁走）。
  两团摆在同一份战斗配置里而不是拆成两场：拆开要多一个战斗 id，
  而脚本侧的调用口径归编剧。近的一团一照面就咬，远的一团在对角——
  追上去是韩立贪心，不是被逼的。
- 角色数值若要再调，**`yu_zitong` 的 `maxHp` 必须一直大于 480**，否则它就成了
  「吞得掉的那一团」，第二场会以 `Won` 收场；`mo_juren_yuanshen` 的 `maxHp`
  必须一直小于 480（且越小吞得越快）。`tests/Ch03ShihaiTests.cpp` 的
  `TheDataHasTwoBallsOneSmallOneBig` 钉着这两条，改坏了会当场转红。

### 5.4 战场登记：法术与物品从哪里来（2026-09-21 补）

> **已被 docs/octopath-battle.md 取代**（八方旅人化改造，2026-09-25）：登记表口径不变；不伤人的法术在菜单上的理由改成「不是伤人的法术」（新文档 2.7）。

契约 2.3 节要求「毒的来源是物品与法术，两者都走既有的 `Item` / `Magic` 数据」。
这一节补的是**那两条路怎么通到战斗里**——此前它们根本没通：
`BattleState::addMagic` / `addItem` 在产品代码里一次都没被调用过，
于是 `checkCast` 的第一句 `findMagic` 必然落空，每一场战斗里施法都被拒，
战斗中用物品同理，用毒系统只在手搭的夹具里跑过。

登记由 `BattleScene::buildFromSetup` 在 `battle_.setup()` 之后做（`setup` 会清表）。

| 登记什么 | 范围 | 判据 |
| --- | --- | --- |
| 法术 | 场上各单位在 `data/roles/*.magics` 里声明的那些，取**并集** | 编成说了算，不是整张 `data/magics` 表 |
| 物品 | 玩家背包里**战斗中真有效果**的那些 | `core::battleUsable(item)`：`restoreHp` / `restoreMp` / `poison` / `curesPoison` 任一非零 |
| 识海（`terrain == "mind"`） | **一件都不登记**，法术与物品都是 | 明写的例外，见 3.5 的更正 |

三条口径的理由：

- **法术取并集而不是整张表。** `checkCast` 的老口径是「`Unit::magics` 留空 =
  战场登记的法术都会」，所以登记范围直接决定了杂兵能放什么。把整张表摆上桌，
  每一场仗都会把全作十四章的法术发给场上每一个没声明法术又有法力的单位。
- **并集还不够，得让「不会」说得出口。** 并集里仍然有别人的法术。
  `core::battle::Unit` 因此加了 `magicsExhaustive`（缺省 `false`，保住老口径给
  手搭夹具用），**game 层建场时对每个单位一律置 `true`**：`data/roles` 里那份
  `magics` 就是这个角色会什么的全部答案，声明了几条就是几条，一条没声明就是
  一条都不会。data 里真有会出事的编成——`b11_ningcuidao_youyao` 把 `maxMp 120`
  却一条法术没声明的三级海兽，和会海潮诀的四级海兽摆在同一张图上。
- **韩立因此在战斗里一条法术也放不出来**，这是如实反映 data：既没有 `hanli`
  这个 role，`GameState` 里也没有已习得法术这一项，全作没有任何一处写着他会
  什么法术。宁可他暂时不会，也不能靠「留空 = 全会」把敌人的法术顺手塞给他——
  第 3 章教学战里那样一来，玩家能放的唯一一条法术会是僵兽的**尸毒爪**。
  这条缺口记在 `docs/tech-debt.md` G-4：data 哪天给了他法术，这里自然就亮了。
- **物品按效果分，不按 `kind`、更不按物品 id。** 毒药、解毒药、丹药的真实条目
  由编剧写，game 层与 core 层都不该认识它们的名字。按 `kind` 分也不行：`pill`
  里既有回血的金疮药，也有纯剧情用的筑基丹（restore 全是 0），而灵草里的黄精草
  是真能当场嚼的——真正的分界线是效果。判据只有 `core::battleUsable` 一处，
  将来 `Item` 加了新的战斗效果字段，改那一处，登记范围自动跟上。

**背包扣减在 game 层**（`BattleScene::issuePlayerAction`）：core 只认战斗里的效果，
不持有玩家的物品栏。登记表是开战那一刻的快照，用光最后一颗之后它还留在表里，
所以那个入口在 `apply` 之前先问一句背包够不够——不问的话，最后一颗丹药能被
反复用到天荒地老。**玩家发起的动作一律走这一个入口**，包括将来的动作菜单。

**键盘目前给不出 `Cast` 与 `Item`**：七个键（四方向 + 确认 + 取消 + 菜单）已经
用满，要一个动作菜单才放得下，而那是 `ui/` 层的活，不在这一批的改动范围里。
记在 `docs/tech-debt.md` G-5。登记与扣减这条链路本身已经通了，也有测试钉着
（`tests/Ch03BattleKitTests.cpp`），菜单接上来只是多一个调用方。

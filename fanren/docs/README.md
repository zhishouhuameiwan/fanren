## 三条反复踩的坑（本工程各自栽过多次，写在这里省得再栽）

1. **判断文件的编码、行尾、字节内容，只能用 Python 读字节。**
   不许拿 `grep`、`file` 或编辑器显示当判据。终端代码页是 GBK，UTF-8 中文在终端里
   显示成乱码是正常的，不代表文件坏了。本工程在这上面栽过六次。
   构建日志是混合编码，读字节后按 `gb18030` 解码。
   调 `tools/novel/novel.py` 一律带 `PYTHONIOENCODING=utf-8`。

2. **bash heredoc 会吃掉反斜杠转义。** 已栽过四次，最严重的一次把校验器正则里的
   `\b` 变成了退格字节，检查器从此什么都匹配不到、永远报通过。
   凡内容含 `\` 的文件，用 Write 工具直接写，不要用 heredoc。

3. **通过的闸门不证明任何事，除非闸门本身被负向验证过。**
   校验器、测试、地图属性、分支可达性都在这上面出过事。
   新加的每一处检查，都要配一条「故意写坏 → 确实被抓住」的用例。

4. **做负向验证时，先确认跑的是新编出来的二进制。**
   把源码改坏、还原时若 mtime 没往前走，ninja 会跳过重编，于是你看到的红灯或绿灯
   来自**上一次**的二进制。第 2 章的闭环测试第一轮红灯就是这么来的，作废重跑才发现。
   还原后显式拨新 mtime（`os.utime`），或核对二进制的时间戳，不要只看测试输出。

### 判据自己会说谎的几种长相（都实际发生过）

上面第 3、4 条是同一件事的两面。已知的空转法列在这里，写断言时逐条对照：

| 长相 | 为什么会空转 | 堵法 |
| --- | --- | --- |
| 正则被吃掉转义 | 什么都匹配不到，永远报通过 | 负向用例：故意写坏 → 必须被抓住 |
| 「找不到某个词就算过」 | 被查字符串变成空的时候照样通过 | 先验判据：那个字符串必须真的有内容 |
| 禁词表被清空 | 扫描器还在跑，只是无词可扫 | 另立一条用例先验扫描器本身有没有牙 |
| 比值判据「≥ N 倍」 | 分母塌成 0 时恒真 | 先验分母 > 0 |
| 只钉一个数据点 | 另一条同样错的曲线只要穿过该点就蒙混过关 | 扫一片，或另钉住曲线本身 |
| 陈旧二进制 | 改了源码但没重编，看的是上一次的结果 | 见第 4 条 |
| **把内容形状当成规格** | 断言「所有的 X 都…」，而那只是**今天碰巧的样子**。内容一长大它就转红，而红的不是代码、是断言自己 | 写之前问一句：这是契约写死的规则，还是当前仓库的普查？规则要能在内容翻倍后仍然成立 |
| **读错了日志** | 每个会话有自己的构建槽（`build_slot.bat`），日志名跟着槽走。读默认的 `build.log` 会读到**别人**的构建结果 | 先看文件 mtime 对不对得上自己刚才的动作；槽名见 `build_slot.bat` |

| **判据自己会挑起点** | 一条通关测试如果可以自己决定从哪儿开始，它证明的就只是「在某个起点上剧情走得通」。第 4 章的 `kStartRealm` 是照着「怎么才能让这条测试绿」反推出来的，而文件头**诚实地写明了这一点**——写明一件事不等于那件事可以成立 | 章与章之间的存档首尾相接。手搭起点可以，但每个与上一章不同的字段都要有一行注释说明它怎么变过来的 |
| **判据对自己的取舍敏感** | 驱动被测物的那只手若有多个同样合理的取舍（先吃药还是先出手、吃哪一瓶），而换一个取舍就换一个结论，那这条判据量的是它自己的脾气，不是被测物。第 4 章七组实测里翻面的编成换了三回，而 `data/battles/` 一个字节没动 | 拿一只手去量平衡之前，先确认它自己是稳的。详见 `docs/tech-debt.md` G-11 |

**「把内容形状当成规格」已经以三种面貌出现过**：第 1 章是地图对象计数与传送点目的地，第 2 章是收益倍数，第 4 章是「仓库里每一场战斗都是单波」——最后这一条尤其说明问题，**它恰恰因为多波次功能真的做成了而转红**。契约写的是规则（「没声明波次的按单波跑」），测试写成了普查（「今天有几场」）。
同一批里还有一条挑错了样本：它拿「野狼帮来犯」当「不变的那一场」的例子，而那一场从设计上就注定要变成多波次。**拿一个注定要变的东西当不变的例子，只是把红灯往后拖。**

**「读错了日志」这一条实际发生过，而且伪装成了一个内存安全问题**：默认槽里有别的会话
留下的陈旧目标文件（`sizeof(Application)` 是旧的），测试崩在 `0xc0000374` 堆损坏。
在自己的槽 `build-<会话前缀>.log` 里，同一份源码 529 个测试全绿。
**排查前先确认日志的 mtime 与自己刚才那次构建对得上**，否则查的是别人的树。

## 并行作业的边界（第 2 章用八个代理并行，实测出来的）

第 2 章同时开了八路作业。产出很好，但并行本身付出了可观的代价，记在这里，第 3 章照这个改。

**实际发生的冲突：**

- 共享的 `build/` 被抢占：`LNK1104: 无法打开文件 fanren_tests.exe` 反复出现；
  有一次 `build.log` 被锁，主构建脚本整个空跑却报成功。
- 有人在 `build.bat` 运行中改了它，cmd 读到半截脚本，门禁全过却报退出码 1。
- 共享树被改成编译不过三次（删了 `markTriggered` 但测试没跟、用了还没落地的新字段），
  别人只能在隔离副本里继续干活。
- 两名代理撞进了同一个任务（生成器地雷），所幸收敛而非互相覆盖。
- 一个代理为了躲开构建锁另建了 100 MB 的独立构建目录。
- `tests/ScriptApiTests.cpp` 的夹具用固定临时目录名 `%TEMP%\fanren_script_api_root`，
  两个 ctest 进程同时跑会互删目录，造成偶发红灯——这是并行放大的既有缺陷。

**下一章照这几条做：**

1. **派活时把「战场」写成文件级白名单，不是描述性的一句话。** 第 2 章写的是
   「你的战场是 X、Y、Z」，仍然撞车；要写成「只准改这几个文件，其余一律先问」。
2. **一次只让一路碰 `build/`。** 需要并行验证的，各自用独立构建目录，
   并在收尾时自己删掉。
3. **不要把两件都要改同一个文件的事同时派出去**，哪怕改的是不同的行。
4. **测试夹具一律用唯一目录名。** 固定临时路径在串行时看不出问题，一并行就成偶发红灯。
5. **收尾串行化。** 最后的构建与门禁由主控一个人跑，不要几路同时收尾。

### 补记：第 2 章复审期间树仍未冻结（第二次了）

上面那条「收尾串行化」是第 2 章整改前写下的，**整改收尾时我自己没照做**：
复审与闭环测试两路同时在跑，于是复审方的 C++ 突变验证被别人的
`fanren_tests.exe` 锁住链接目标（`LNK1104`），`build.log` 被对方的门禁运行覆盖，
他们只好改用两条不依赖构建的证明。复审报告里原话是「这是第二轮快照锁定的请求未被理会」。

**教训比规则本身更要紧**：写下规则不等于执行规则。审查阶段尤其如此——
审方需要一棵不动的树，而这一点在派活的那一刻很容易被「反正他们改的文件不重叠」说服。
文件不重叠不够，**构建产物是共享的**。

下一章的做法：**复审开始前停掉所有其他代理**，审方独占仓库与 `build/` 直到出裁决。

### 第三条坑的一个变体：判据是从被测物推导出来的（第 3 章实测）

第 3 章最要害的缺陷——两种杀的触发方式装反——**四条测试对它满格敏感，却一条也没发现**。
整改方的剖析值得全文记住，它是第 3 条坑（「通过的闸门不证明任何事」）的一个新形状：

1. **触发方式从来没被断言过，只被「使用」过。** 驱动函数在它不对时会响亮地失败，
   于是那组测试对它有满格敏感度，**却没有任何独立的「应该是什么」**。
   这是最坏的组合：它一定会红，但它红的是「地图变了」，不是「地图错了」。
2. **驱动方式是照着被测物写出来的。** 触发方式当时只有 tmj 一个地方说得出口，
   作者自然是读 tmj 写驱动。
   **从被测物推导出来的判据，永远发现不了被测物与规格不一致——它只发现得了被测物发生了变化。**
3. **错的行为长出了配套设施，于是看起来像是有意为之。** 装错的那个 enter 触发压在必经门洞上，
   逼得走位层专门加了绕开它的辅助函数、在文件头写了一段理由，
   最后甚至把这个副作用**写成断言**。到这一步，地图、驱动、散文三样互相印证，
   唯一的异议者是一句没人读的脚本注释。
4. **点名守这件事的那条测试量错了轴。** 「两种杀的操作感」是两件事——
   戏里发生了什么，与玩家是怎么让它开始的。判据只覆盖了前者，后者根本没有裁判。

**怎么防**：凡设计文档写死的取值（触发方式、once、射程、上限……），
要有一条**不经过驱动、直接读数据、判据写死成设计原文**的断言。
形状要与主测试**不同**——同一套驱动写两遍，只是把同一个错误钉两遍。

**一条绿着的、钉住错误行为的测试，比一条没牙的测试更难发现**：没人会去动一条绿的。

## 一个模块「可用」需要三样齐备（撞了三次才总结出来）

规则层造好了 ≠ 游戏里能用。完整的链条是三段，缺任何一段，模块都是死的：

| # | 环节 | 典型症状 |
| --- | --- | --- |
| 1 | **规则层** `src/core/rules/` | 多半早就有了，而且有单测 |
| 2 | **加载器** `src/io/` | 数据目录里有文件，但没人读它 |
| 3 | **游戏层入口** `src/game/` | 规则能算，但玩家没有任何办法触发它 |

**前三次撞上的都是后两样缺其一，而且每次都是等到写那一章的内容时才发现：**

- 第 2 章前：P2 的七个规则模块（掌天瓶、灵田、修炼……）全都够不着——缺第 3 段。
- 第 3 章前：战斗的法术与物品**从未被登记过**，`Cast` / `Item` 是死代码——缺第 3 段。
  用毒系统因此只在测试里跑过。
- 第 4 章前：炼制系统一次调用都没有，配方**连加载器都没有**——第 2、3 段都缺。

**已知还差的（第 4 章盘点，别再等撞上）：**

| 模块 | 缺什么 |
| --- | --- |
| `rules::Encounter`（随机遭遇） | 缺加载器 + 入口。`data/encounters/` 有 3 张表，地图里 0 个遭遇对象，而规范与门禁都已支持 |
| `rules::Economy` 的拍卖那一半 | 缺数据目录 + 加载器 + 面板 |
| `rules::Realm::demote`（境界跌落） | 零调用方，第 9 章要用 |
| `data/quests/` | 空目录无加载器——不是「够不着」，是**还没造** |

**开新章之前先照这张表查一遍**，比写到一半撞上便宜得多。

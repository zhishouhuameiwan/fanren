## engine 平台层与中文排版

验收时间：2026-09-20 · 实现方：专职代理（opus）

### 1. 硬约束核验

| 判据 | 方式 | 结果 |
| --- | --- | --- |
| 公共头文件不含 SDL 类型 | grep `Engine.h` / `TextLayout.h` 是否出现 `SDL_` / `TTF_` / `MIX_` / `IMG_` | **无命中，pimpl 全藏在 .cpp，通过** |
| 契约签名一致 | 逐条比对 30 个公共声明与 `interfaces.md` 第 1、1.1 节 | 无改动，通过 |
| 测试通过 | 主控亲自跑 `build/fanren_tests.exe` | **126/126 通过** |
| 排版测试量 | 要求至少 12 个，实交 25 个（LayoutText 12 + Kinsoku 7 + Graphemes 6） | 通过 |

### 2. 值得记下的实现决定

- **排版的不变式测试**：对 6 种输入 × 5 种行宽交叉断言「只重排空白、绝不吞字」。
  这比逐例断言更能守住边界，因为病态输入组合穷举不完。
- **禁则的悬挂上限**：行首禁则每行最多拉回 2 个字符，否则连续标点串会被整段吸到第一行；
  行尾禁则同样设上限，避免把行挤空导致孤立括号无限下坠。两类禁则字符集不相交，先拉后推不会震荡。
- **超长无空格串按字符硬切**：契约的「西文不断词」按「放得下时」理解。300px 的词塞进 200px 的框，
  不切就会画到框外。
- 字体按目录扫描取首个，不硬编码文件名，换字体不用改代码。系统字体回退保留为临时退路并打警告。

### 3. 裁决

**CMakeLists.txt 的改动：批准。** 代理动了我划的禁区但「先做后报」，理由成立——
`fanren_tests` 原本不链接 `fanren_engine`，engine 的测试根本无法链接，「亲自跑通」不可能。
两处改动都已复核正确：

1. `fanren_engine` 加进测试链接的 foreach。
2. 运行时库拷贝**注册在 `gtest_discover_tests()` 之前**。这个顺序是硬要求：
   POST_BUILD 按注册顺序执行，而测试发现会启动可执行文件，库没到位则发现阶段直接失败。

ui 层将来要测时同样加进 foreach。

### 4. 主控推翻的一条报告（判据可靠性）

代理报告「仓库里所有文件都是 CRLF，改成 LF 后被环境改回，建议加 `.gitattributes`」。

**这条不成立。** 主控用字节级统计复核（读文件 bytes，分别统计回车加换行的字节对、与不带回车的孤立换行字节）：

| 文件 | CRLF | 纯 LF |
| --- | --- | --- |
| CMakeLists.txt | 0 | 219 |
| docs/interfaces.md | 0 | 342 |
| src/core/Result.h | 0 | 25 |
| src/engine/Engine.h | 0 | 72 |
| tools/validate.py | 0 | 459 |
| build.bat | 51 | 0（故意，批处理需要 CRLF） |

全部源文件本来就是纯 LF。主控先用 grep 按行尾回车符统计同一批文件，它报出 100% CRLF，
$'` 跑同一批文件，它报出 100% CRLF，
与字节级结果完全矛盾——**Git Bash 这一层有转换，拿它判断行尾不可靠**。

本项目已有一条同类教训：终端代码页是 GBK，肉眼看终端中文同样不可信。
**判断文件编码与行尾，一律读字节。** 已回告代理，不做无谓的归一化。

### 5. 遗留

代理另起了一个独立的代码审查通道（内存安全、UTF-8 解码越界、禁则两个 pass 的迭代器失效与终止性），
结果未到。若返回高危问题，由代理继续修并回报。

# P2 模块验收

## 模块 A 修炼与时间（Calendar / Cultivation / Bottle / Field）

验收时间：2026-09-20 · 实现方：专职代理（opus）

### 1. 硬约束核验

| 判据 | 方式 | 结果 |
| --- | --- | --- |
| core 零依赖 | 查四个头文件的实际 include 行 | 只有标准库与 `Realm.h`，通过 |
| 测试通过 | 主控亲自跑测试二进制 | 61 个用例全过，全量 296 全绿 |
| 编译警告 | 全量日志（按 gb18030 解码）| 零警告 |
| 未动他人文件 | 构建脚本 SHA256 前后一致 | 通过 |

> 注：主控初次用 grep 查依赖时命中了四个头文件，一度以为违反约束。
> 实为误报——命中的是注释里「不依赖 SDL / JSON / 文件 IO」这句话。
> **匹配到词不等于存在依赖**，同判据可靠性那条教训。

### 2. 值得记下的数值设计

- **失败倒扣按关口门槛的比例，不按当前总修为**。炼气期与结丹期的失手痛感因此是同一量级，
  都等于退回两成进度；按绝对值扣的话后期等于不痛。
- **突破的成功判定取第一次随机数，倒扣与走火用第二次**，并对 399 个种子逐一断言
  「丹药绝不会把成功翻成失败」。嗑了丹药反而炸炉是玩家最不能接受的随机。
- **灵草计价用平方曲线**，百年为基价的 121 倍，硬判据留了三倍余量而非擦线通过。
  一滴绿液把十年草推到二十年，净赚超过那株草本身的价值——这是玩家宁可等瓶子
  也不肯贱卖的理由，有专门测试锁住。
- **催熟取「翻倍且至少加十年」而非固定加年份**：保底让刚播的种苗浇一滴也有意义，
  否则玩家会攒着绿液不用，循环卡在起点。

### 3. 代理自己指出并由主控裁决的漏洞

**掌天瓶绿液无容量上限。** 挂机一百年凝五千余滴，配上超线性计价就是无需任何技巧的
无限刷钱。代理发现后**报告而非擅自加**，主控裁决补上，并特别要求：容量满时不得继续
累积欠账。只夹住滴数却照常推进计时，等于一腾出空位就一次性灌进来，闸门形同虚设。

代理的实现分三条路：已满则把计时拨到当日、零头一并作废；中途灌满同理；未触上限维持
原行为（这条不能动，否则每天点开瓶子界面就把进度清零）。

并自行补了一条未要求的防御测试：容量为 0 或负数（存档未初始化、上层忘了按境界赋值）
时宁可一滴不出，也不让上限判断反向。

主控独立复核了关键测试的断言内容：满瓶跨一百年后消耗一滴，当日与第六日均不返还，
等满一个完整周期才给出第三滴。判据严格，通过。

### 4. 其余三项裁决（均维持代理现状）

| 项 | 裁决 | 理由 |
| --- | --- | --- |
| 催熟是否加随机 | 不加，保持确定性 | 原著里绿液是稳定能力不是赌博；确定性让「攒几滴浇哪株」成为可计算的决策，加随机只会让人存读档 |
| 灵草差异化成熟期 | 暂不加 | 现无灵草数据支撑，加了是空设定。将来改为接一张表，而不是往槽位结构里塞字段 |
| 打坐收益的小数余数 | 不在规则层保底 | 代理指出设每日保底会被拆成一天一次打坐刷十倍收益。余数累加器放上层 |

### 5. 待办

- 灵草差异化成熟期：内容生产阶段有具体灵草后，`growField` 接 `seedId → 成熟参数` 表。
- 打坐余数累加器：上层状态里加字段，让每日打坐在界面上看得见进度。

# 《凡人修仙传》RPG · 完全重构方案

> 目标：以原著《凡人修仙传》为蓝本，做一款复现原著流程、人物、道具、法宝、丹药、剧情的单机修仙 RPG；
> 至**乱星海篇结束（韩立启动传送阵返回天南）**时，**首次游玩者主线 + 必经支线 ≥ 10 小时**。
>
> 状态：**v2 已拍板（2026-09-20）**，第 9 节七项全部按推荐选项执行。原著文本已就位于 `H:/Work/Kys/novel`。
> 当前阶段：**P0 进行中**。P0 的校对结论若与本文第 5 节冲突，以 `docs/lore/` 下的校对文件为准，本文在 P0 收尾时统一修订为 v3。

## 0. 一句话结论

现有三个子项目都不能通过"继续堆内容"达到 10 小时目标：内容全部硬编码在 C++ 里（改一句话要重编译）、地图靠代码手搓、剧情被压缩成十几个节点、且存在原著还原错误（如"金精竹"应为"金雷竹"）。
建议**新开一个工程 `fanren/`**，采用 **SDL3 + 数据驱动（JSON）+ Tiled 地图 + Lua 事件脚本** 的架构，把现有代码里成熟的规则（战棋、炼制、掉落、境界曲线）迁移为可单测的纯逻辑层，然后按"章节即里程碑"生产内容，用**互斥口径的内容预算表 + 内置计时器 + 首次游玩者实测**验收 10 小时。

## 1. 现状评估

### 1.1 三个子项目对比

| 项目 | 规模 | 技术 | 内容 | 结论 |
| --- | --- | --- | --- | --- |
| `fanren-kys` | 13.2k 行 C++ | Win32 + GDI 软件帧缓冲，winmm 合成音，零依赖 | 33 角色 / 54 物品 / 11 法术 / 20 战斗 / 16 子场景 / 19 个目标节点 / 对白约 1 万字 | 系统最全（战棋、炼丹、制符、布阵、掉落、秘境、情缘），但内容与地图全在 C++ 里；估算实际游玩 1.5–3 小时 |
| `fanren-sdl3` | 2.7k 行 C++ | SDL3 + SDL3_ttf（vendor 预编译包 + bootstrap.py），规则库 + 自动跑通测试 | 11 个"章节"= 11 场战斗，12 件物品，单张大地图 | 架构方向对（规则层无 SDL 依赖、有 bot 测试），但内容只是原型；估算 30 分钟 |
| `kys-cpp` | 33k 行 C++ | SDL3 全家桶 + vcpkg，grp/idx 资源，RunNode 场景栈，Cifa 脚本，三种战斗模式 | 金庸群侠传 | 只作架构与战斗 AI 参考；资源格式与金庸强绑定，不宜直接 fork |

### 1.2 fanren-kys 的结构性问题（重构的动机）

1. **内容硬编码**：`StoryEvents.cpp` 2223 行 C++ 脚本、`StoryData.cpp` 658 行数据、`StoryMaps.cpp` 639 行用 `MapBuilder` 画地图。每加一段剧情要改枚举 `StoryIDs.h`、重编译。10 小时内容意味着对白 13 万字量级、地图 50+ 张，这条路会崩。
2. **ID 靠枚举顺序**：`buildStoryData()` 按枚举顺序注册，插入一条中间数据全盘错位。
3. **剧情标志是 `int flags[512]`** 的魔数索引（如 `getFlag(84)`），无法维护。
4. **渲染层与逻辑层耦合**：`BattleScene.cpp` 1560 行里战斗规则和绘制混在一起，无法单测。
5. **GDI 软件渲染 + 程序生成像素**：以后换素材、加特效、做分辨率适配都受限。
6. **原著还原偏差**：README 把青竹蜂云剑材料写成"金精竹"（原著为**金雷竹**）；乱星海篇被压成 4 个目标节点；天南七派、魔道六宗只在对白里报了名。
7. **无测试、无内容校验工具**，十几万字的内容没有工具兜底必然出错。

### 1.3 值得保留的资产

- `fanren-kys`：境界/五行/灵根规则、战棋战斗流程、炼丹/制符/布阵规则、随机掉落、小瓶催熟经济循环、情缘系统——这些是**规则**，迁移到新工程的纯逻辑层。
- `fanren-sdl3`：`bootstrap.py` 下载校验预编译包、`RepeatGate` 输入、`RulesTests` 里"BFS 自动走图 + 自动打赢"的 bot 思路。
- `kys-cpp`：`Event.cpp` 的指令集清单（约 200 条，作 Lua API 蓝本）、战棋 AI、UI 绘制顺序文档、RunNode 的绘制栈思路（但不沿用其嵌套阻塞 `run()`，见 3.5）。

### 2.2 "10 小时"的定义

三个互斥的时长桶：

| 桶 | 内容 | 是否计入 10 h 门槛 |
| --- | --- | --- |
| A 主线 | 主线对白、剧情战斗、必经地图的探索移动 | 计 |
| B 必经支线/系统 | 主线前置的资源获取：种药、炼丹、坊市采买、猎妖令、拍卖会等**玩家实际操作**时间；闭关/跳时不计 | 计 |
| C 可选内容 | 可选支线、秘境刷取、图鉴收集、情缘互动 | 不计门槛，只计"正常游玩"总量 |

- **门槛**：≥ 3 名**首次游玩**的测试者（非开发参与者），按同一份"玩家画像 checklist"游玩（完成 ≥ 60% 支线、图鉴 ≥ 50%、参加 ≥ 1 次拍卖会），到"乱星海篇·终"字幕时，游戏内计时器读数**中位数 ≥ 10 h**，且每人 A+B ≥ 8 h。
- **计时器规则**（防刷）：两个计时器，"系统菜单"（存读档/设置/暂停）不计，"玩法菜单"（炼制/商店/图鉴/修炼面板）计；连续 60 s 无有效输入即暂停计时；每个主线里程碑写入时间戳，验收看里程碑分布，不只看总数。
- **bot 不给时长**：无头 bot 只输出结构指标（主线节点数、必打战斗数、必经地图数、必需资源量），时长由真人抽样标定"每类节点秒数"后换算，写入 `tools/audit.py`。

## 3. 技术方案

### 3.1 技术选型

| 层 | 选型 | 理由 / 落地要点 |
| --- | --- | --- |
| 语言/构建 | C++20，CMake ≥ 3.25，Ninja，MSVC v145（VS2026） | 与现有工程一致，环境已验证 |
| 平台层 | SDL3 3.4.16 + SDL3_ttf 3.2.2 + SDL3_image 3.4.6 + SDL3_mixer 3.2.4 | **P0 探针已实测四库同时链接并运行通过**，四者均有官方 VC 预编译包，经 `bootstrap.py` 下载并 SHA256 校验。注意 image 已移除 `IMG_Init`，mixer 重构为 `MIX_*` 对象模型，见 `docs/deps.md` |
| 数据 | JSON（nlohmann/json 单头文件） | 字符串 ID；**one-file-per-entry 或按章分片**，避免多代理同改一个大文件冲突 |
| 地图 | Tiled `.tmj` + PNG tileset | 60 张地图必须用编辑器；对象层放 NPC/事件/传送点；`docs/map_spec.md` 先行 |
| 剧情脚本 | Lua 5.4.9（源码内建，按 C 编译）+ sol2 3.3.0 | 改剧情不重编译；**协程 yield/resume 已由探针实测通过**，3.5 节并发模型有实证支撑。`/bigobj` 探针规模下非必需，作防御保留 |
| 文案 | `data/text/chapterXX.json`（key → 文案），Lua 只引 key | 字数统计、校对、返工可自动化；避免 Lua 字节串处理中文 |
| 测试 | GoogleTest（FetchContent，`gtest_force_shared_crt=ON`） | 规则层零 SDL 依赖 |
| 依赖管理 | 统一写进 `docs/deps.md`：预编译包走 bootstrap.py + 哈希；源码依赖走 FetchContent 并锁 tag | 三种来源必须有锁定机制 |
| 字体 | 随包 OFL 中文字体 | 不依赖系统字体 |
| 美术 | 第一阶段程序生成像素导出为 PNG tileset 占位，后续整包替换 | 渲染层只认 tileset + 图集 JSON，代码里不画像素 |

不选：fork `kys-cpp`（依赖与资源格式剥离成本高）、继续 GDI、C++ 注册事件。

### 3.2 分层架构与依赖方向

```
fanren/
├── CMakeLists.txt / CMakePresets.json / bootstrap.py / build.bat / play.bat
├── src/
│   ├── core/        规则层：零 SDL、零文件 IO，只操作已解析的结构体
│   │   ├── model/       Item/Role/Magic/Gongfa/Recipe/Shop/Battle/Encounter/Quest 结构
│   │   ├── world/       GameState、时间、命名旗标、队伍、背包/储物袋、图鉴、计时器
│   │   ├── rules/       境界、五行、修炼、突破、炼制四艺、掉落、情缘
│   │   └── battle/      战棋规则与 AI（纯逻辑）
│   ├── io/          JSON 加载/校验、存档序列化与迁移、Tiled 解析（不依赖 SDL）
│   ├── script/      Lua 绑定：EventAPI 只产出"命令对象"入队；协程调度器
│   ├── engine/      SDL3 平台层：窗口、渲染、图集、字体与中文排版、输入、音频、分辨率适配
```

### 3.5 脚本并发模型（Lua 协程 × 场景状态机 × 存档）

这是审阅指出的最大设计缺口，规则写死如下：

1. **不使用嵌套阻塞 `run()`**。场景是一个由主循环驱动的状态栈，每帧 `update/draw`，没有 C++ 递归事件循环。
2. **Lua 事件在协程里跑**。`talk()`/`battle()` 等 API 在 **Lua 侧**实现为：构造命令对象 → `coroutine.yield(cmd)`。yield 发生在 Lua 代码里，不跨 C 调用边界，绕开 "attempt to yield across a C-call boundary"。
3. **game 层每帧取出待执行命令**，推入对应场景（对话框、战斗场景、淡入淡出），命令完成后把结果 `resume` 回协程。
4. **协程挂起态禁止存档**：存档菜单只在"无活动事件"时可用；事件本身设计为短原子段（对话→选择→战斗），战斗内提供的"战斗中存档"改为战斗开始前的自动存档点。
5. **热重载口径**：P1 只承诺"重启生效"；运行时重载 Lua/JSON 作为 P2 可选项，且仅限"非战斗、非对话"状态。
6. 协程生命周期绑定到触发它的场景实例；场景弹出时若协程未结束，视为脚本错误并写日志（开发期直接断言）。

### 3.6 存档

- JSON 文本 + `save_version` + 校验和（防手改污染验收）+ 迁移函数表；8 档 + 自动存档；两个计时器与里程碑时间戳随档保存。
- 随机生成物品存完整实例。
- `tests/save_migration/` 保存每个 schema 版本的样本档，每次 schema 变更必须通过旧档加载测试。

## 4. 玩法系统设计

### 4.1 核心循环："掌天瓶经济"

```
时间流逝 → 小瓶凝液（前期 7 日一滴，境界提升后加速）
        → 催熟灵草（年份跳跃：十年 → 百年 → 千年）
        → 炼丹 / 出售 / 换筑基丹与结丹材料 / 炼器材料
        → 修为、灵石、法宝 → 推进主线与突破
```

- 灵草有**年份**属性，价格与丹方要求按年份算（沿用现有实现）。
- **循环从第 2 章起闭合**（审阅意见）：神手谷药园给 2 个临时种植槽、墨府后院 3 个，百草园（第 5 章）扩到 8 个，荒岛洞府（第 8 章）另开 6 个。
- 小瓶到手时间与首个灵田时间之间不允许超过 20 分钟主线。

### 4.2 境界与时间

- 境界：凡人 → 炼气一至十三层 → 筑基初/中/后 → 结丹初/中/后。**乱星海篇末境界为 P0 硬约束项**（校对后定死，P5 不得再改），数值曲线按该上限反推。
- 时间系统是成长的一部分：年龄与寿元显示；"闭关 N 年"作为大跨度跳时；小瓶、灵草、坊市货、秘境冷却、拍卖会档期都按日历走。跳时不计入游玩时长。
- 突破：修为圆满 + 丹药/机缘 + 资质与功法加成 → 概率判定；失败有代价（修为回退、走火）。

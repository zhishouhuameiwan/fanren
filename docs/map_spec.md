# 地图规范（Tiled）

> 适用于 `fanren/maps/` 下全部 `.tmj` 地图。关卡代理必须严格遵守本规范；
> `tools/validate.py` 按本文逐条校验，不合规的地图不得合入。
>
> 版本 1.0 · 2026-09-20 · P0 交付物

---

## 1. 基础参数

| 参数 | 值 | 说明 |
| --- | --- | --- |
| 逻辑分辨率 | 1280 × 720 | `SDL_SetRenderLogicalPresentation`，整数缩放到窗口 |
| 瓦片尺寸 | 32 × 32 px | 全项目统一，不得混用 |
| 可视范围 | 40 × 22.5 格 | 由逻辑分辨率推出；地图小于此值时居中留边 |
| 地图格式 | Tiled JSON（`.tmj`） | 不使用 `.tmx`；Tiled ≥ 1.10 |
| 图块层格式 | CSV | 不使用 base64/zlib，保证 git 可读可 diff |
| 坐标系 | 左上角为 (0,0)，x 向右、y 向下 | 与引擎一致 |

地图尺寸建议：

| 类型 | 建议格数 | 备注 |
| --- | --- | --- |
| 室内（房间、洞府、店铺） | 24×18 – 40×30 | 一屏到两屏 |
| 村镇、宗门、坊市 | 48×36 – 64×48 | |
| 秘境、战场 | 40×30 – 80×60 | |
| 世界地图 | 128×96 | 每个地区一张，共 2 张 |

## 2. 图块集（tileset）

- 全部使用**外部 tileset**（`.tsj`），放在 `maps/tilesets/`，地图通过相对路径引用。禁止内嵌 tileset。
- 每张 tileset 对应一个 PNG，PNG 与 `.tsj` 同名同目录。
- 命名：`terrain_<地区>.tsj`（地表）、`prop_<主题>.tsj`（建筑与装饰）、`char_<主题>.tsj`（人物与生物）。
- 一张地图引用的 tileset 不超过 4 个，避免 firstgid 混乱。
- 新增瓦片只允许**追加**到 PNG 末尾，不得插入或重排，否则已有地图的 gid 全部错位。

---

## 3. 图层结构（顺序与命名固定）

自下而上，名称**区分大小写**，缺一不可（可以为空层）：

| # | 图层名 | 类型 | 用途 |
| --- | --- | --- | --- |
| 1 | `ground` | tilelayer | 地表：草地、土路、地板、水面 |
| 2 | `overlay` | tilelayer | 地表叠加：花草、裂纹、阴影 |
| 3 | `building` | tilelayer | 建筑主体、墙体、岩壁（角色在其后） |
| 4 | `front` | tilelayer | 遮挡层：树冠、屋檐、前景（绘制在角色之上） |
| 5 | `collision` | tilelayer | 碰撞：非 0 即不可通行；只用一种标记瓦片 |
| 6 | `objects` | objectgroup | 全部交互对象，见第 4 节 |

约定：
- 渲染顺序 `ground → overlay → building → 角色 → front`。
- `collision` 层在游戏中不渲染，仅供引擎读取；在 Tiled 中设为半透明便于编辑。
- 不得新增图层；确需分层时在 `objects` 里用对象类型区分。

## 4. 对象层 schema

`objects` 层中每个对象必须设置 **Tiled 的 Class 字段**（即 `type`），并按下表提供自定义属性。
对象的 `name` 在同一张地图内必须唯一，采用 `<type>_<语义>` 形式（例：`npc_han_sanshu`、`portal_to_market`）。

对象位置一律使用**矩形**，并对齐到瓦片网格（宽高为 32 的整数倍）。

### 4.1 `spawn` — 出生点 / 入口

每张地图**至少一个**，`default` 为真者有且仅有一个。

| 属性 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 是 | 入口标识，被 `portal.target_spawn` 引用 |
| `default` | bool | 是 | 是否为默认入口 |
| `facing` | string | 是 | `up` / `down` / `left` / `right` |

### 4.2 `portal` — 传送点 / 出入口

| 属性 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `target_map` | string | 是 | 目标地图 id（文件名去扩展名） |
| `target_spawn` | string | 是 | 目标地图中的 `spawn.id` |
| `require_flag` | string | 否 | 需要该旗标为真才可通行 |
| `deny_text_key` | string | 否 | 不满足条件时的提示文案 key。**有 `require_flag` 就必须有它** |
| `transition` | string | 否 | `fade`（默认）/ `none` |

**`deny_text_key` 一律按「目标图」命名**：`<目标图的章号>.block.<目标图去掉 chNN_ 前缀>`。
例：`ch01_hanjiacun` 里通往 `ch01_qingniuzhen` 的那道闸门，key 是 `ch01.block.qingniuzhen`。
读法是「被拦在青牛镇门外时说的那句话」，文案内容则讲你**当下这张图**还有什么没办完。

为什么不能按源图命名：一张图可以有好几个带闸门的出口——`ch02_yaopu` 就有三个
（居所 / 外刃堂 / 崖壁），按源图命名时三条不同的文案都叫 `ch02.block.yaopu`，表达不了。
目标这一侧天然唯一：一道闸门就是「拦住你进某张图」这一件事。

第 1 章一度按源图、第 2 章按目标图，两套并存过一阵。那时八条文案内容都是对的，
只是没有单一约定可供机器校验，下一个写地图的人只能靠猜。现在由规则 20 盯着。

### 4.3 `npc` — 角色

| 属性 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `role_id` | string | 是 | 对应 `data/roles/` 中的角色 id |
| `script` | string | 否 | Lua 脚本路径，相对 `scripts/` |
| `facing` | string | 是 | 朝向 |
| `wander` | bool | 否 | 是否随机走动（默认 false） |
| `visible_flag` | string | 否 | 该旗标为真时才出现。不出现时不画、不能对话、**也不占格** |
| `hidden_flag` | string | 否 | 该旗标为真时隐藏。隐藏时同样不画、不能对话、**也不占格** |

### 4.4 `trigger` — 事件触发区

| 属性 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `script` | string | 是 | Lua 脚本路径 |
| `mode` | string | 是 | `enter`（踏入）/ `interact`（按键交互）/ `auto`（进图即触发） |
| `once` | bool | 是 | 是否只触发一次 |
| `guard_flag` | string | 否 | 触发的前置旗标 |
| `set_flag` | string | 是（当 `once=true`） | 判定「已触发过」所看的那个旗标 |

#### `once` 的判据：脚本自己置的完成旗标（2026-09-20 改）

**`once=true` 的触发器必须写 `set_flag`，指向脚本在演完之后置位的那个完成旗标。**
引擎据此判断这个触发器是否已经用过，**不再另外预写任何内部记号**。

改这一条是因为旧实现有个陷阱：记号在脚本**执行之前**就打上了。于是任何
「先查前置条件，不满足就说一句话然后 return」的脚本，被踩一次就把触发器永久烧掉，
玩家条件满足后再来，触发器已经没了。这类脚本在内容层是常态，第 2 章五个段落的
推进全是这种结构。

新口径不需要作者记住任何新规矩：脚本本来就在末尾置完成旗标，而提前 return 的路径
根本走不到那一行，所以触发器自然留着可重演。

配套的三点行为：

- **脚本报错或被丢弃** → 完成旗标没置 → 触发器留着，可以重演。比旧实现严格更好。
- **`once=true` 却漏写 `set_flag`** → 退化成可重复触发。这是故意选的失败方式：
  它响亮、试玩第一下就看得见，而不是像从前那样生造一个没在 `data/flags.json`
  登记、任何工具都查不到的内部旗标。校验器在门禁上拦这种写法。
- **`once=false` 却留着 `set_flag`** 同样报错——多半是写漏了 `once`。

### 4.5 `encounter` — 遭遇区

| 属性 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `table_id` | string | 是 | 对应 `data/encounters/` 的遭遇表 |
| `steps_min` | int | 是 | 触发所需最少步数 |
| `steps_max` | int | 是 | 触发所需最多步数 |
| `daily_cap` | int | 否 | 每游戏日触发上限（防刷，默认 8） |

### 4.6 `facility` — 设施

炼丹炉、器炉、灵田、打坐处、商店、任务板、存档点等统一用本类型。

| 属性 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `kind` | string | 是 | `alchemy` / `forge` / `talisman` / `formation` / `field` / `meditate` / `shop` / `board` / `save` |
| `ref_id` | string | 否 | 商店 id、灵田 id 等 |
| `slots` | int | 否 | 灵田槽位数（`kind=field` 时必填） |
| `grade` | int | 否 | 炉鼎 / 符笔 / 地火 / 阵盘的品阶 0-5，缺省 1；`kind` 为炼制四艺之一时有意义。缺字段按 1 收而不是 0：0 在规则层的意思是「没有炉鼎」，一处忘了写的丹房会变成点不动任何东西的屋子 |
| `require_flag` | string | 否 | 解锁旗标 |

### 4.7 `battle_anchor` — 战斗地形锚点

标记该地图上可发生战棋战斗的区域，供战斗场景取地形与单位初始位置。

| 属性 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `terrain` | string | 是 | `field` / `indoor` / `cave` / `secret` / `battlefield` / `sea` / `mind` |
| `ally_zone` | string | 是 | 我方初始区矩形，格式 `x,y,w,h`（格） |
| `enemy_zone` | string | 是 | 敌方初始区矩形 |

## 6. 命名规范

| 对象 | 规则 | 例 |
| --- | --- | --- |
| 地图文件 | `ch<章号>_<地点拼音>.tmj`，通用地图用 `common_` | `ch01_qingniucun.tmj` |
| 地图 id | 与文件名同（不含扩展名） | `ch01_qingniucun` |
| 旗标 | `<域>.<语义>`，全小写下划线 | `mo.duoshe_started` |
| 文案 key | `<域>.<场景>.<序号>` | `ch02.mo_return.q1` |
| 脚本 | `scripts/ch<章号>/<事件>.lua` | `scripts/ch02/mo_return.lua` |

全部标识符使用**拼音或英文**，不含中文、空格、连字符。中文只出现在文案 JSON 里。

> **脚本为什么按章分组而不是按地图分组**（2026-09-20 修订）：
> 初版规范写的是 `scripts/ch<章号>_<地点>/`，由脚本模块在实现中提出异议并被采纳。理由三条：
> ① 事件常常跨地图（一条支线牵涉多张图），挂在某一张图的目录下必然要选一个"主地图"，武断且易错；
> ② 一张地图会承载多章事件（黄枫谷在第 6、7、8 章反复出现），按地图分目录会把不同章的脚本混在一起；
> ③ 文案已经按章分组（`data/text/ch01.json`），脚本跟着章走，两者目录结构对齐。
> 地图的 `trigger.script` / `npc.script` 属性照此引用，例如 `ch01/sanshu.lua`。

## 7. 校验规则（`tools/validate.py` 实现）

地图不合规则**阻塞合入**。校验项：

1. 六个图层齐备、名称与顺序正确、类型正确。
2. 图块层为 CSV 格式；tileset 为外部引用且路径存在。
3. 地图属性八项齐备，`map_id` 与文件名一致。
4. 每张地图恰有一个 `default=true` 的 `spawn`。
5. 每个 `portal.target_map` 存在，且 `target_spawn` 在目标地图中存在（**双向可达性检查**）。
6. 所有 `npc.role_id` 在 `data/roles/` 中存在。
7. 所有 `script` 路径存在。
8. 所有 `*_flag` 属性引用的旗标已在 `data/flags.json` 登记。
9. 所有 `*_key` 文案 key 在 `data/text/` 中存在。
10. 所有 `encounter.table_id` 在 `data/encounters/` 中存在；`steps_min ≤ steps_max`。
11. 对象 `name` 在图内唯一；对象矩形对齐 32 px 网格。
12. `collision` 层与 `building` 层一致性抽查：`building` 有实体瓦片处 `collision` 应非 0（报警告不阻塞）。
13. **连通性**：从 `default` spawn 出发做 BFS，所有 `portal`、`npc`、`facility`、`trigger(mode=interact)` 必须可达，否则报错。
    **BFS 走的是引擎口径**：`collision` 非 0 ∪ **不带 `visible_flag` / `hidden_flag` 的** `npc` 矩形 ∪ 全部 `facility` 矩形。
    **不在场的 NPC 不占格**：`WorldScene::tryStep` 走 `visibleNpcAt`，它挡不挡路随旗标变，算不得墙。
    `facility` 没有可见性属性，一律占格。
    （2026-09-21 改：此前隐身的 NPC 照样占格，是一堵没有任何反馈的隐形墙。）
    早先这条只看 `collision` 层，于是一张把 2×2 设施压在唯一走廊上的地图能通过校验、却走不过去。
    走得到之后按不按得出来是另一回事，见规则 17。
14. `chapter` 属性与所在目录/文件名的章号一致。
15. **`once` 与 `set_flag` 配对**（见 4.4）：`once=true` 必须有 `set_flag` 且它已在
    `data/flags.json` 登记；`once=false` 不得留着 `set_flag`。
16. **踏入型对象自身要踏得响**：`portal` 与 `mode=enter` 的触发至少要有一格可走且可达。
    够得着不算——站在旁边按不出来的传送点等于不存在。
    同一格上若有无 guard 且非 once 的 `enter` 触发抢在前面 return，传送点同样踏不响，一并报错。

> **规则 17 覆盖到哪里**（2026-09-21 实测确认，别再加重复的检查）：
> `interact` 那条路与 `tryStep` 那条路**各查一遍**。
> `tryStep` 那一段按 `objectAt` 的真实行为建表（不分 mode 只取第一个），
> 所以**两个 `enter` 触发叠在一格上必然被报**，带不带 `guard_flag` 都一样——
> 实测把一个现成的 enter 触发原样复制叠上去，两种情形都报「踏不响：被同类靠前的 X 抢先命中」。
> 「无 guard 且非 once」那道过滤只用在 **portal 被 enter 触发挡住** 那一支上，
> 不适用于触发器之间。

17. **同格遮蔽**：一格上只问得出一个对象，压在下面的那个永远按不出来。
    `WorldScene::interact` 依次问 `npc` → `mode=interact` 的 `trigger` → `facility`，
    谁先应声谁就独占这一次确认键；而引擎每类只取第一个**命中且在场**的
    （`npc` 走 `visibleNpcAt`，其余走 `objectAt`）。
    于是两种死法，都不会有任何工具报错，玩家只觉得按键没反应：
    - **跨类**：有脚本且无 `visible_flag` / `hidden_flag` 的 NPC 压住同格的 `facility`；
    - **同类**：对象表里靠前的压住靠后的——哪怕靠前的那个没脚本、本来就不该应声。
      但**带 `visible_flag` / `hidden_flag` 的 NPC 不在此列**：它不一定在场，既压不住谁也不占「第一个命中」的位子。
      **同格摆两个 NPC、各带互补旗标**，是给一个格子挂两段剧情的唯一办法
      （一个 `npc` 对象只挂得住一个 `script`），这种写法合法。

    只报**必然**遮蔽：带 `visible_flag` / `hidden_flag` 的 NPC、带 `guard_flag` 或
    `once=true` 的触发器都会让位，不算遮蔽（「蒲团上压一段剧情」是有意设计，见 4.4）。
    规则 16 里踏入型那一条是同一族：`tryStep` 中 enter 触发命中就 `return`，排在它
    后面的 `portal` 收不到这一步。

18. **跨图可达性**：每张图都要能从开局地图一路走到。
    规则 13 是**逐图**做的，它只问「这张图里的东西够不够得着」，问不出「有没有人
    通向这张图」。开局地图取自 `src/main.cpp` 的 `loadMap("ch01_hanjiacun", "")`，
    改开局要一并改 `validate.py` 的 `START_MAP`。

    推演走的是 **(地图, 落点)** 二元组而不是地图：从哪个 `spawn` 落地，决定了你在
    这张图里走得到哪几个出口——「进得去」不等于每个出口都用得上。`require_flag` 在
    这一条里不参与（它拦的是时机，不是通路，那归规则 19）；脚本里的 `teleport()`
    算一条边，有的图按设计只能靠剧情进去，那不叫断链。

    这一处不是假想：神手谷南墙那个通往第 2 章的 `portal_to_ch02_yaopu` 一旦掉了，
    ch02 的四张图会整体从游戏里消失，而每一张单看都完全合规、规则 13 一个字都不说。

19. **旗标顺序**：每道闸门的旗标都要拿得到，即存在一条合法的推进顺序。
    规则 18 把 `require_flag` 当空气算，问「有没有路」；这一条接上旗标，问「按旗标
    的先后走不走得通」。**两条共用同一段不动点推演，只差一个开关，差集就是顺序
    死锁：门是通的，钥匙锁在门后。**（分开各写一遍迟早会算出两种互相矛盾的「可达」。）

    报两类：因旗标顺序而掉出去的图（纯断链归规则 18 报，不重复）；以及
    `require_flag` / `guard_flag` / `visible_flag` 指向了从开局永远置不上的旗标。
    旗标的来源只有两处，静态算得全：Lua 的 `flag.set` 与对象的 `set_flag`——
    C++ 侧没有任何字面量 `setFlag`，`Application.cpp` 那一处是从 Lua 透传下来的。

    口径刻意宽松，只报**必然**的死锁：脚本里任何一处 `flag.set(X)` 都算拿得到 X，
    不做分支分析（否则每个二选一都会变成一条噪音）；`hidden_flag` 不拦（旗标只增
    不减，玩家总能赶在它置上之前先把事办了）；遮蔽不参与推演（规则 17 已经报过）。

    这份宽松是有来历的：两个「图上看着像环」的样例实测**都不是**死锁——一个是同一个
    脚本同时挂在 NPC 和触发器两处，另一个是绕一圈回头再来。一条「见环就报」的实现
    会在这两处误报，`validate_selftest.py` 的 F4 就是为它们留的对照。

20. **`deny_text_key` 与 `require_flag` 成对，且按目标图命名**（命名规则见 4.2）。
    三种写法都判错：
    - 有 `require_flag` 没有 `deny_text_key` —— 引擎 `showMessage("")`，被拦的玩家
      只会觉得按键没反应。**拦住却不说明还差什么，等于没拦。**
    - 有 `deny_text_key` 没有 `require_flag` —— 引擎只在拦下时播它，这条文案永远
      播不出来，是个会骗人的摆设，十有八九是 `require_flag` 写漏了。
    - `deny_text_key` 不等于 `<目标图章号>.block.<目标图短名>` —— 约定不成文就会
      分叉，分叉之后「这个 key 取对了吗」就不再是机器能回答的问题。

    两者皆无的普通传送点不在此列，那本来就合法。

> 规则 21–28 管地图名 key、目标链、任务、破势与蓄劲、路径行动、野外遭遇与脚本 bgm，
> 条文见 `tools/validate.py` 各条的文档串及其所引的接口文档，本节不重复。下面两条又回到地图本身。

29. **出门方向守恒、按住不回弹**：从 A 图的 `portal` P 走出去、落进 B 图的 `spawn` S，
    (a) S 的 `facing` 必须等于 P 的**出门方向**；(b) 落地后按住进门时那个方向键不松手，不许一路走回 A 图。
    - **为什么**：`WorldScene::update` 是 `keyDown` 加步进冷却，按住就一直走，进门那一刻玩家多半还按着方向键。
      落点若离回程门只有一两格、又正对着它，不松手就被送回 A，再按又被送回来——**两张图之间来回弹**，玩家根本进不去。
      朝向反了是「衔接掉头」：人明明在往南走，一进门转身朝北；朝左右是拐弯。每张图单看都合规，规则 5 / 13 / 16 / 18
      全绿，只有真人按着方向键走一遍才发作——第 1 章「韩家村 → 青牛镇」就是这么上线的：从韩家村南口往下走，
      落在青牛镇最下面、离回村的门两格、朝向还反了，多按一下「下」就弹回村里。
    - **挡路**与规则 13 同一口径（`WorldScene::tryStep`）：越界、`collision` 非 0、`facility` 矩形、**不带**
      `visible_flag` / `hidden_flag` 的 `npc` 矩形；带旗标的 NPC 与 `enter` 触发不挡。
    - **进门方向**：对 P 的每一格 c、每个方向 d（上下左右），c−d 在图内、不属于 P、不挡路（c 自己也得不挡路，
      踩不上的格子从哪面都进不来），d 就是一个进门方向。集合为空说明这道门踩不上去，归规则 16，本条跳过。
    - **出门方向**：贴上边（`y==0`）为上、贴下边（`y+h==H`）为下、贴左边（`x==0`）为左、贴右边（`x+w==W`）为右
      ——哪怕是侧身挤进去的，出了这条边地理上就是往那边去了；同时贴两条边（墙角、横贯整条边的门）只认进得去的那一条。
      不贴边的内门：只有一面进得去就是那一面；几面都进得去就**没有**出门方向，(a) 改问「`facing` 是不是其中一面」
      ——`ch01_qixuanmen` 的 `portal_to_caixiashan` 下、左、右三面都进得去，落点朝下合规。
    - **(b) 的走法**：对每一个进门方向 d，从 S 所在格按住 d——下一格挡路就停；否则走过去；踩上某个 `portal` Q
      就停（同格几道门取对象表里靠前的，同 `objectAt`）。Q 的 `target_map` 是 A 就报，写明走了几步、踩上的是哪道门。
      进门时按的是哪个键，落地后就还按着哪个键，所以走的是**进门方向**，与 S 的朝向无关。
    - 目标图、落点找不到归规则 5。脚本 `teleport()` 不在本条范围：剧情传送的落点与朝向由剧本定，玩家那时也没在走路。
    - `validate_selftest.py` 的 R 节：造一处掉头且回程门就在跟前的衔接，(a)(b) 都得报；只把落点朝向拧 90°，只许报 (a)；
      上面那道三面可进的内门不许报，把落点改朝进不去的那一面必须报。

30. **同一张图上同时在场的 NPC 不重名**：同一张图上两个 `npc` 用同一个 `role_id` 就报错，报错写明图、role 与冲突的对象名。
    比的是**名牌上的字**：`role_id` 不同、但 `data/roles/<id>.json` 的 `name` 相同，同样报错，写明两个 role 与那个名字
    ——新建 role 时照抄了旧 role 的名字，照样会冒出第二个「卖药郎」（引擎画名牌取的就是这个 `name`，查不到角色时写 `role_id`）。
    同 role 的只按同 role 报一条，不因为同名再报一遍。
    - **为什么**：名牌写的是 role 的名字，role 一样名字就一样，玩家分不出谁是谁、该找哪一个问话。role 存在（规则 6）、
      走得到（规则 13）、按得出来（规则 17），样样合规，满街却站着三个「卖药郎」——青牛镇 6 个路人复用了 3 个打探
      NPC 的 role，就是这么上线的。
    - **放行两种**，此外一律报：
      - **轮流在场**：一个的 `hidden_flag` 恰等于另一个的 `visible_flag`。旗标只增不减，任何时刻至多一个在场。
        「同一个人换一段剧情」就这么写（一个 `npc` 对象只挂得住一个 `script`）：`ch02_wairentang` 的
        `npc_li_feiyu` / `npc_li_feiyu_ch03`、`ch02_yaopu` 的两个药圃管事。
        「都带了旗标」「挂着同一个旗标」都不算——两个都写 `visible_flag=X`，旗标一置两人一起出现。
      - **群像白名单**（`validate.py` 的 `CROWD_ROLES`，每个 role 写明理由）：目前只有 `mofu_huyuan`——南城墨府门口
        刻意并排站了 4 个护院，名牌已做防重叠（`WorldView` 画名牌时撞上了就往上叠一行）。两个人的 role **都**在白名单里
        才放；只有一边在，另一边就是个恰好同名的别人，照报。往里加之前先问：玩家看见
        两块一模一样的名牌，会不会以为是同一个人、或者以为找错了人？多数时候会，那就去 `data/roles/` 另建一个角色。
    - 口径与规则 17 的「只报必然」相反，**可能同框就报**：旗标之间谁先谁后静态推不全，而修法很便宜——另建一个 role，
      或者把两人的旗标写成互补。
    - `validate_selftest.py` 的 S 节：把一个没旗标的 NPC 复制成同 role 必须报、且只报一条；同一对写成互补旗标、或换成
      白名单里的 role 不许报；两个都挂同一个 `visible_flag` 仍然必须报；孪生换成照抄了名字的新 role 必须报，写成互补
      旗标则不许报。

## 8. 工作流

1. 关卡代理在 Tiled 中作图，另存为 `.tmj`（CSV 图块层）。
2. 本地跑 `python tools/validate.py --maps` 自检。
3. 全绿后提交；CI 的 validate 步骤会再跑一次。
4. 新增 tileset 瓦片只追加不插入；新增旗标先在 `data/flags.json` 登记再使用。
5. 地图改动若影响主线通路，须跑无头 bot 回归确认该章仍可通关。

### 三道门禁（都在 `build.bat` 里，缺一不可）

| 命令 | 通过标志 | 它防的是什么 |
| --- | --- | --- |
| `python tools/validate.py` | `VALIDATE_OK` | 地图本身不合规 |
| `python tools/mapgen/genmaps.py --check` | `MAPGEN_IN_SYNC` | 生成器与仓库地图漂移（全部 10 张）|
| `python tools/validate_selftest.py` | `SELFTEST_OK` | **校验器自己失灵** |

**三道都排在 `build.bat` 的最前面**（`pushd` 之后、`bootstrap.py` 之前）。它们只要
python 和仓库本身——不要 vendored 依赖、不要 MSVC 工具链、不要网络——所以一张坏地图
几秒钟就报出来，而不是等一轮完整编译加 509 条单测。

它们原先排在最后，代价在 2026-09-21 当场兑现过：一次与内容无关的 ctest 抖动
（测试可执行文件正被重新编译，509 条里 213 条 Not Run）让 `goto failed` 直接跳过了
三道门禁，连跑两遍都没跑到。**只在别的步骤都通过之后才运行的闸门不是闸门。**

第二道是有来历的：生成器早先不产出 `require_flag` / `deny_text_key` / `guard_flag`，
谁重跑一次就会静默抹掉 14 处闸门（含第 2 章的入口），而校验器只报得出其中 1 条。
手工改过的地图属性必须能被生成器重新产出，否则重跑即破坏。

这道门禁一度只盯第 1 章那六张：第 2 章的四张图同样由 `genmaps_ch02.py` 产出、
同样带闸门（`ch02.renyao_done` / `ch02.dazuo_done` / `ch02.duan2_start`），却没有
任何东西在盯——同一个缺口换了一章。现在 `genmaps.py --check` 覆盖全部 10 张，
`genmaps_ch02.py --check` 也能单独跑自己那五张（四张 + 神手谷的南口）。
**新增一章就要把它的生成器接进这道门禁**，否则那一章等于没有第二道闸门。

第三道是本项目最贵的一条教训的制度化：**通过的闸门不证明任何事，除非闸门本身被负向验证过。**
`validate_selftest.py` 造出一批故意写坏的地图，逐条断言校验器确实抓住了它们。
往 `validate.py` 里加新检查，就要往自检里加对应的坏样例，否则那条检查等于没加。
